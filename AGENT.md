# Project Notes For Coding Agent

## Project Identity

- Название проекта: `ScannerAI` / `Сканер документов AI: PDF`.
- Тип проекта: Android-приложение для сканирования документов с локальным OCR и AI-анализом через backend-прокси.
- Основной стек: Kotlin, Android, Jetpack Compose, Clean Architecture, Koin, Room, CameraX, OpenCV, Tesseract, Ktor client, RuStore Pay SDK.
- Backend: отдельный Kotlin/Ktor-сервис `LLMProxy`, путь к нему задаётся ключом `BACKEND_PATH` в `local.properties`.
- Основной Android-модуль: `composeApp`.
- Основной пакет Android-кода: `ru.aiscanner.docs`.
- Целевой магазин: RuStore. Приложение должно работать без Google Play Services.
- Не переносить в проект правила, названия, ресурсы и документацию из других репозиториев без явной просьбы пользователя.
- Не считать предположительно связанные проекты частью этого репозитория, пока связь не подтверждена файлами проекта или пользователем.

## Question Handling Rules

- Если пользователь задает вопрос, сначала ответить на него текстом и не редактировать код или файлы автоматически.
- Это правило действует и для вопросов, которые выглядят риторическими или подразумевают возможную правку.
- Переходить к изменениям только после явной просьбы сделать, исправить, заменить, реализовать или удалить что-либо.
- Если запрос одновременно содержит вопрос и явную команду на изменение, сначала кратко ответить на вопрос, затем выполнить изменение.

## Scope And Change Rules

- Изменять только файлы, необходимые для текущей задачи.
- Не выполнять попутный рефакторинг, переименование или форматирование несвязанных участков без отдельной просьбы.
- Не менять публичные контракты, форматы данных, миграции, конфигурацию окружения и поведение совместимости без явной необходимости.
- Перед изменением существующего поведения найти его реализацию, связанные вызовы, конфигурацию, тесты и документацию.
- Не считать найденный похожий код автоматически относящимся к задаче: проверить фактические связи.
- При неоднозначности предпочитать минимальное изменение, сохраняющее текущее поведение вне заявленной задачи.
- Не редактировать сгенерированные и сборочные каталоги: `.gradle`, `.kotlin`, `build`, `composeApp/build`, `backend/__pycache__`.

## Architecture Rules

- Соблюдать текущую Clean Architecture-структуру Android-кода:
  - `core/` - базовые типы, ошибки, диспетчеры и DI.
  - `domain/` - модели, геометрия, бизнес-логика, контракты репозиториев и use cases.
  - `data/` - Room, файлы, обработка изображений, OCR, AI-клиент, PDF-экспорт, billing и аналитика.
  - `presentation/` - Compose-экраны, ViewModel, `UiState`/`UiEffect`, навигация и тема.
- Между экранами передавать только идентификаторы и легковесные параметры, не тяжелые изображения или тексты документов.
- Тяжелые операции с изображениями, OCR, PDF, БД и сетью выполнять вне Main Thread.
- Сохранять неразрушающую модель обработки: оригинал изображения плюс параметры фильтра/обрезки.
- Координаты обрезки хранить и передавать в нормализованном виде относительно исходника, если это соответствует существующему коду.
- Для новых зависимостей сначала проверить `gradle/libs.versions.toml`, существующие паттерны DI и доступность без GMS.

## Privacy And Security Rules

- Не хардкодить секреты, ключи, токены, приватные URL и параметры подписи в исходниках.
- API-ключи AI-провайдера должны жить только на backend или в переменных окружения, не в APK.
- Не писать в логи тексты документов, OCR-результаты целиком, изображения, PDF, персональные данные, ключи и ответы провайдера, если они могут содержать пользовательский текст.
- AI-функции отправляют только текст после явного согласия пользователя; изображения документов не отправляются.
- Release без `RELEASE_BACKEND` должен отключать AI-функции понятным образом, а не показывать фиктивные результаты.
- Mock AI и stub-подписки допустимы только в debug. В release не добавлять обходы реального backend или RuStore Pay SDK.
- Keystore и пароли подписи использовать только из переменных окружения или GitHub Secrets.

## Android Code Rules

- Писать Kotlin в стиле существующего кода проекта.
- Для строк в Kotlin предпочитать строковые шаблоны: `"Документ $documentId обработан"`.
- Для сложной сборки строк использовать понятные локальные переменные или `buildString`, если это улучшает читаемость.
- Новые UI-состояния оформлять через существующие `UiState`/`UiEffect`-паттерны.
- Compose-экраны держать предсказуемыми: бизнес-логику выносить во ViewModel/use case, тяжелые операции не выполнять прямо в composable.
- Для ошибок использовать существующие `AppResult`/`AppError` и локальные паттерны обработки.
- Для новых публичных или нетривиальных классов, use case, контрактов и функций добавлять или обновлять KDoc.
- Не добавлять зависимости от Google Play Services: проверять альтернативы, совместимые с RuStore и AOSP-устройствами.

## Backend Code Rules

- Backend `LLMProxy` - отдельный Ktor-сервис, а не место для хранения пользовательских документов.
- Рабочий backend для AI-запросов должен находиться по пути из `local.properties`: ключ `BACKEND_PATH`.
- URL backend для debug-сборки брать из `local.properties`: ключ `DEBUG_BACKEND`.
- URL backend для release-сборки брать из `local.properties`: ключ `RELEASE_BACKEND`.
- `local.properties` не попадает в git; в каждом инстансе репозитория `BACKEND_PATH`, `DEBUG_BACKEND` и `RELEASE_BACKEND` нужно прописывать отдельно.
- Сохранять ограничения backend: лимит размера текста, rate limiting, таймауты, строгая валидация структурированных JSON-ответов и отсутствие текстов документов в логах.
- При изменении AI-запросов сохранять требование: модель возвращает только JSON по ожидаемой схеме и не выдумывает отсутствующие данные.
- Не менять endpoint-контракты `/v1/auth/rustore`, `/v1/ai/summarize`, `/v1/ai/extract`, `/v1/ai/contract`, `/health` без синхронного обновления Android-клиента и документации.
- Новые настройки backend добавлять через переменные окружения и документировать в `README.md` или `.env.example` проекта по `BACKEND_PATH`, если они нужны пользователю.

## Local Search Rules

- Для поиска файлов и текста сначала использовать `rg` / `rg --files`, если он корректно работает в текущей среде.
- На этой машине `rg`/`ripgrep` может падать с `Access is denied`; в таком случае повторить поиск через PowerShell с явной фильтрацией директорий и расширений.
- Текстовые файлы проекта сохранены как UTF-8 без BOM, а Windows PowerShell 5.1 без явного параметра может читать их как ANSI/1251 и ломать русский текст в mojibake.
- Для чтения текстовых файлов в PowerShell указывать `-Encoding UTF8`: `Get-Content -LiteralPath path\to\file.md -Encoding UTF8`.
- Для поиска по содержимому через PowerShell указывать `-Encoding UTF8` у `Select-String`.
- Если вывод выглядит как `РќР°...` или `Р”Рѕ...`, считать чтение некорректным и повторить команду с явным `-Encoding UTF8`.
- Не читать и не искать без явной необходимости в тяжелых/сгенерированных каталогах: `.git`, `.gradle`, `.kotlin`, `build`, `composeApp/build`, `.idea`, `.venv`, `venv`, `__pycache__`, `tmp`, `temp`, `coverage`.
- Широкий поиск ограничивать исходниками, ресурсами и документацией: `.kt`, `.java`, `.xml`, `.gradle`, `.kts`, `.md`, `.txt`, `.yaml`, `.yml`, `.json`, `.properties`, `.toml`, `.py`, `.sh`, `.ps1`, `.conf`.
- Не запускать широкий поиск по бинарникам и артефактам: `.db`, `.sqlite`, `.sqlite3`, `.bin`, `.jar`, `.aar`, `.apk`, `.aab`, `.dex`, `.so`, `.dll`, `.exe`, `.class`, `.zip`, `.7z`, `.gz`, `.tar`, `.png`, `.jpg`, `.jpeg`, `.webp`, `.gif`, `.pdf`.
- Если нужен файл внутри тяжелого каталога, читать только конкретный известный файл или короткий точечный фрагмент.

## Build And Verification Rules

- Основные команды проекта описаны в `README.md`: `./gradlew test`, `./gradlew :composeApp:detekt`, `./gradlew :composeApp:assembleDebug`, `./gradlew :composeApp:connectedDebugAndroidTest`.
- Не запускать Gradle, Android Studio build-команды, emulator/instrumented tests или release-сборки без явной просьбы пользователя.
- Если проверка нужна, но запуск тяжелый или требует Android SDK/эмулятор/секреты, честно указать это и предложить точную команду.
- Для backend можно использовать локальные проверки Python/FastAPI только если они не требуют сетевых ключей и не обращаются к реальному AI-провайдеру.
- После изменения кода всегда сообщать, какие проверки были выполнены, а какие не запускались.

- В документации фиксировать только проверенные сведения; непроверенные гипотезы выносить в отдельный раздел `Гипотезы`.
